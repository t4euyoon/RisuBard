# 플러그인 성능 수정 전후 비교와 채택 판단

> 아래는 측정 당시 기록이다. 후속 적용에서 객체 재사용 저장은 제거했고, 호스트 설정을 구현했다. 현재 동작은 [최종 적용 문서](asset-maid-performance.md)를 참고한다.

이 문서는 앞선 `asset-maid-performance.md`의 객체 재사용 권고를 정정한다.
현재 전체 객체를 재귀 비교하는 저장 수정은 확정하지 말고 철회하는 것을 권한다.
이번 작업은 비교·판단이며, 호스트 설정 UI 구현이나 원격 배포를 수행하지 않았다.
기존 로컬 기능 수정은 그대로 두고 측정 코드와 보고서를 추가했다.

## 측정 범위

- 로컬 Windows, Vitest 4.1.4 / happy-dom / 실제 Svelte 반응형 객체.
- 합성 대화: 1턴을 사용자·캐릭터 각 1개 메시지로 정의, 200턴=400개 메시지.
- 기본 측정 본문 약 1,963자, 캐릭터당 채팅 하나. 캐릭터 수 1 또는 10.
- 준비 운동 3회 제외, 적용 전후 순서를 교대로 실행, 기본 측정 15회 중앙값.
- 저장 측정은 양쪽에 공통인 수신 스냅샷 생성 시간을 제외한 대입/비교/flush 비용.
- 별도 실제 `Chats.svelte` 테스트: 본문 약 2,000자, 40개 또는 전체 메시지 표시.
  `Chat.svelte` 자식만 빈 대체 컴포넌트로 바꿔 목록 처리와 마운트 수를 측정.
  준비 운동 3회 제외, 9회 중앙값. 브라우저 전체 페인팅/이미지 디코딩은 포함하지 않는다.
- OCI 서버, 실제 사용자 DB, 분석 LLM 및 NovelAI 요청은 사용하지 않았다.
- ms 수치는 이 환경에서의 관찰이며 실제 앱 전체의 속도 배수가 아니다.

## 결과

### 캐릭터 스냅샷: 유지 권장

| 턴/캐릭터 수 | 기존 전체 DB 복사 | 선택한 캐릭터만 복사 |
|---|---:|---:|
| 200 / 1 | 3.66 ms | 3.22 ms |
| 200 / 10 | 35.00 ms | 3.37 ms |
| 2,000 / 1 | 36.12 ms | 35.30 ms |
| 2,000 / 10 | 384.80 ms | 37.50 ms |

캐릭터가 하나일 때 효과는 작고, 다른 캐릭터 데이터가 많을 때 효과가 명확하다.
선택된 캐릭터 자체의 큰 채팅을 복사하는 비용은 남는다.
단순 문자열 필드의 문자를 모두 새 메모리에 복제한다고 해석하면 안 된다.
핵심은 불필요한 객체·배열 순회 및 스냅샷 생성 범위 감소이다.

### 최근 문맥 역방향 탐색: 유지 권장

| 턴 | 기존 전체 탐색 | 수정된 최근 구간 탐색 |
|---|---:|---:|
| 200 | 0.0751 ms | 0.00156 ms |
| 2,000 | 0.7697 ms | 0.00134 ms |

요청된 최근 답변 12개 선택 결과가 같은지 함께 검증했다.
상대 개선은 크지만 절대 시간은 작다. 이것만으로 수초 지연이나 멈춤을 설명하지 않는다.

### 저장 시 변경 없는 객체 재사용: 현 구현 채택 반대

실제 채팅 목록 코드의 결과:

| 턴/표시 메시지 수/변경 | 기존 저장+목록 갱신 | 객체 재사용+목록 갱신 | 새 메시지 컴포넌트 마운트 전→후 |
|---|---:|---:|---:|
| 200 / 40 / 에셋 | 1.92 ms | 4.55 ms | 0→0 |
| 200 / 40 / 마지막 본문 | 2.05 ms | 5.01 ms | 1→1 |
| 200 / 400 / 마지막 본문 | 5.74 ms | 7.86 ms | 1→1 |
| 2,000 / 40 / 에셋 | 14.10 ms | 45.87 ms | 0→0 |
| 2,000 / 40 / 마지막 본문 | 15.70 ms | 55.95 ms | 1→1 |
| 2,000 / 4,000 / 마지막 본문 | 64.83 ms | 90.58 ms | 1→1 |

`Chats.svelte`는 이미 메시지 내용 해시가 같은 컴포넌트를 재사용한다.
이 구현에서는 최상위 캐릭터가 여전히 교체되므로 목록 처리도 다시 실행되며,
재귀 비교 비용이 추가된 반면 마운트 수 감소는 관찰되지 않았다.
이전의 객체 동일성 단위 테스트는 동작 정확성만 확인했으며 실제 이득의 증거가 아니었다.
다른 UI나 플러그인에서의 잠재적 이득은 부정하지 않지만, 이 앱에 전역 적용할 근거가 없다.

## 호스트 설정과 전용 패치

플러그인별 자동 BardWiki 제공 설정(기본 끔)을 권장한다.
원본 플러그인의 API를 그대로 받아 호스트에서 주입 여부를 결정한다.
현재 옵션을 사용한 동일 분기의 통제 실험에서는 5회 조회 시 켬=5회 장식 함수 호출,
끔=0회 호출이었다. 각 호출에 인위적으로 20ms 지연을 넣었으므로 그 시간 결과는
OCI 실제 지연 개선 수치로 사용하지 않는다. 실제 BardWiki 캐시가 적중하면 네트워크
검색은 원래도 발생하지 않으며, 절감량은 캐시와 설정·문맥 갱신에 따라 달라진다.

호스트 설정 UI와 설정 보존 경로는 아직 구현하지 않았으므로 전환 전체를 검증했다고
표현할 수 없다. 구현 후 기본 끔, 즉시 반영, 업데이트 시 유지, 명시적 getContext
유지, 모든 자동 주입 조회 경로 적용을 검증해야 한다.
전용 Asset Maid 패치/생성 스크립트 제거는 그 전환 완료 후 확정한다.
이는 그 자체의 속도 개선보다는 버전별 패치 유지보수를 없애는 변경이다.

## 재현

저장소 루트 PowerShell에서 실행:

```powershell
$env:RISUBARD_PERF_COMPARE = '1'
node node_modules/vitest/vitest.mjs run src/ts/plugins/pluginPerformanceComparison.svelte.test.ts
node node_modules/vitest/vitest.mjs run src/lib/ChatScreens/Chats.pluginPerformance.svelte.test.ts
Remove-Item Env:RISUBARD_PERF_COMPARE
```

결과는 저장소 상위 `.analysis/plugin-performance-comparison.json` 및
`.analysis/plugin-chat-list-comparison.json`에 기록된다. 일반 테스트에서는 건너뛴다.
